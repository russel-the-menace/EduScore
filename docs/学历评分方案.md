# HR 候选人学历评分方案（第一版）

## 1. 设计目标

学历评分应当衡量候选人的教育背景与目标岗位之间的相关性，而不是简单制作“名校排行榜”。建议把学历评分作为招聘决策的一项输入，并同时输出评分依据、数据置信度和风险提示，保证 HR 可以复核。

## 2. 是否评估专业

建议评估专业，但评估的是“专业与岗位的相关性”，不是专业本身的高低。

- 校园招聘、研发、医疗、法律、财会等专业门槛较强的岗位：专业相关性权重可为 20-25 分。
- 通用职能和有工作经验的候选人：专业相关性权重可降至 5-15 分。
- 专业名称匹配应支持“直接相关、相邻相关、可迁移、无明显相关”四级，并允许岗位配置专业白名单和相邻专业组。

## 3. 学历背景总分（100 分）

| 维度 | 建议权重 | 评分原则 |
| --- | ---: | --- |
| 学历/学位层次 | 25 | 按岗位最低要求和最高已验证学历评分，避免重复叠加多段学历 |
| 学校信号 | 20 | 是否为官方名单内院校、办学层次、可配置的权威院校标签；学校名气不应成为主导项 |
| 专业与岗位相关性 | 25 | 根据岗位专业组进行四级匹配；强专业岗位提高权重，通用岗位降低权重 |
| 学科或专业实力 | 10 | 仅在有可靠、可追溯的学科数据时启用，优先于综合排名 |
| 学业表现 | 15 | GPA/排名、荣誉、科研或与岗位相关的项目成果；数据缺失时不直接判低分 |
| 教育证据完整度 | 5 | 学校、专业、学历、时间、证书编号等信息的完整性和一致性 |

建议将“学历真实性验证”作为门槛和风险状态，而不是混入分数。状态可设为 `verified`、`pending`、`inconsistent`、`unverified`，出现疑点时转人工复核。

## 4. 学校信号的 20 分拆分

| 子项 | 分值 | 说明 |
| --- | ---: | --- |
| 官方名单匹配 | 8 | 学校名称或学校标识码能够与权威名单匹配；普通高校和成人高校均可获得认可分 |
| 办学层次 | 4 | 本科、专科等信息用于描述院校培养层次，实际学历层次仍在“学历/学位层次”评分 |
| 可配置院校标签 | 5 | 使用有来源、带版本日期的标签库，禁止在代码中硬编码永久排名 |
| 岗位领域匹配 | 3 | 例如财经、师范、医药、政法等行业特色与目标岗位的匹配程度 |

不建议把“普通高校/成人高校”直接做成固定扣分项。两份名单首先用于确认学校是否合法存在和识别教育类型；是否全日制、实际学历和岗位要求应作为独立字段处理。如果岗位确实存在受监管的学历形式要求，应作为明确规则展示，而不是隐藏在综合分中。

## 5. 不同候选人阶段的使用权重

学历背景分不应始终占候选人总分的相同比例：

| 候选人阶段 | 学历背景占候选人总评建议权重 |
| --- | ---: |
| 应届生/无全职经验 | 25%-30% |
| 1-3 年经验 | 15%-20% |
| 3-8 年经验 | 8%-12% |
| 8 年以上经验 | 5% 左右 |

其余权重应分配给岗位技能、相关经验、工作成果、结构化面试和必要的测评。强准入岗位可以按法规或职业资格要求设置门槛，不必靠提高学校权重实现。

## 7. 第一版实现建议

第一版使用可配置的规则引擎，不建议一开始训练机器学习模型。权重、分档、岗位专业组和院校标签应放在 JSON/YAML 或数据库中，保留规则版本、数据来源和生效日期。积累足够招聘结果数据后，再评估预测效果和不同群体之间的差异，决定是否引入统计模型。

推荐后端使用 Python：

- Python 3.12+
- FastAPI + Pydantic：提供评分 API 和输入校验
- SQLAlchemy + PostgreSQL：保存学校库、规则版本、岗位配置和评分记录
- RapidFuzz：处理学校曾用名、简称和轻微拼写差异
- pytest：覆盖分数边界、缺失字段、同名学校和人工复核场景

原型阶段可先使用 SQLite，前端再按团队习惯选择 TypeScript/React。Python 更适合当前的数据清洗、名称匹配、规则计算以及后续可能的数据分析，因此建议将评分核心放在 Python 服务中。
